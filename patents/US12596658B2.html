按命令与数据 beat 组合调度手机 AP 互连

Mechanisms for arbitrating among packets in one or more co-packaged integrated circuits

一条写消息的数据占两个周期，读请求只用命令线。怎样让两条总线在等待空隙里同时有效工作？

  • 核心结论

  • 前轮有无赢家，以及下游能否吸收发包，决定是否切换规则
  • 组内 QoS 份额由虚拟通道计数管理

核心结论

fabric 把纯命令和带数据包分开仲裁。发现相邻上一轮空闲且下游通路允许时，参考更早的历史再选带数据包，留下下一数据 beat 所在的命令槽供纯命令使用。

命令只占一个位置，数据可能还要继续传输

0022–0033 说明手机 SoC 的 CPU 与内存控制器可经各自 fabric 跨 die 访存，0038–0040 明确 application processors 和 L2。0051–0052 的仲裁可在接口、交换机、代理或内存控制器。0170–0175 给出电池移动设备和 LPDDR 实施例。

图 1 给出 AP 内存请求经过网络接口的一段。纯命令和带数据的包分开排队。上行读请求可能没有数据，写请求可能有写数据。下行读响应通常带数据。内存控制器的 DRAM 命令调度在后面，图中的周期属于 fabric。

图 2 重建说明书举例。最早的写包已占 t0、t1 的数据槽，t1 没有读请求可补。t2 两类都有效时，LRG 可能先选读，数据线就有空拍。先发第二个写包，t3 可以用命令线发读，同时传剩余写数据。这个例子的最后数据 beat 提前一周期。

逐周期模型固定三笔到达和两拍写数据。允许两轮历史触发切换时，数据空拍从 1 拍降到 0 拍，读命令从立即发出变成等待 1 拍。将历史窗扩大到四轮后，同一序列不再触发这次切换。模型记录 fabric 发包与数据续拍，量化的是这组输入下的仲裁取舍。

前轮有无赢家，以及下游能否吸收发包，决定是否切换规则

图 3 按权利要求 2 和说明书原图 6 标出切换条件。紧邻前轮有赢家时，可沿用 LRG 选择另一类别。若前轮空闲，只有频差未达阈值且最旧的固定窗轮次已有赢家，才可用 non-LRG。下游缓冲 token 可以作为判断不同速率带来回压的一个信号。

说明书 0070 对较慢远端的描述举过非 LRG 的相反例子。图 5、6、0083–0092 以及权利要求 2 给出了更具体的有 token 与无 token 规则。本图按这些具体证据。最早轮次为纯命令时，下行还可能使用不同选择。

组内 QoS 份额由虚拟通道计数管理

图 4 把 pure command 和 command-data 分成两个仲裁组。每组可以按 VC 计数选择候选，有多个 subchannel 时还可先做组内 LRG。权重作为这次获选后计数递增量，较小权重可让较严格时延的 VC 更频繁回到低计数。

测试应同时看命令占用、data beat 空槽、读请求等待和相同配置下各 VC 的服务份额。遇到下游变慢时还要量化缓冲水位和 token 归还，判断换策略是否把空拍变成回压。
