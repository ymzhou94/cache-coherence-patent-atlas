根据共享 BIU 拥塞标记迁移单个 CPU 线程

CPU cluster shared resource management

同一 CPU cluster 的互连接口拥塞时，系统怎样发现相关线程，并把它与同组的其他线程分开调度？

核心结论

性能控制器先测 BIU 请求队列满周期占比并保留过载标记，再在调度回调中使用当前线程的 LSU 微操作指标判断资源使用。OS 调度器更新对应线程标记，可以把该线程放到另一 CPU cluster，其他同组线程继续在原处运行。

找出拥塞的资源，再确定测量对象

同一 CPU cluster 的多个核心共享末级缓存（LLC）及总线接口单元（BIU）。本案的 LLC 是 CPU cluster 本地的最后一级缓存，说明书允许它是 L2。miss 请求可经 BIU 发往互连，继续访问系统缓存或主存。

图 1 上路展示从 LLC 缺失到互连。下路展示控制器怎样读 BIU 计数器。队列满周期占比以队列为满的 BIU 周期数作分子、总 BIU 周期数作分母。控制器对该比值做用于迟滞的滤波，再比较可调阈值。第 7 项还允许用 LLC 的 load 缺失比例辅助判断 BIU 饱和。

历史过载怎样归因到单个线程

CPU cluster 的过载标记保存过去采样时段的状态。图 2 中，OS 调度器为当前线程发起回调后，性能控制器先查这个标记。标记有效才查看当前线程在核执行的 LSU 微操作指标等观测，判断它是否使用以前出现过载的资源。

示例可每隔几毫秒采集 CPU cluster 的硬件计数器，在十几微秒量级的调度回调中使用结果。两者分别观察共享接口的历史状态和当前线程使用资源的情况。图表 3 给出两个判断怎样共同决定是否更新线程标记。线程标记可随线程迁移。

单线程迁移改变了谁使用哪个 BIU

原图 3C 将线程 2.C 从 P-core cluster 3 放到 P-core cluster 2，使其可以用目标 CPU cluster 的 BIU。图 4 并列画出未移动的同组线程和移动线程的后续路径。两组 CPU cluster 可以采用相同的核型；选核决定与 DVFS 运行点各有控制对象。

迁移的收益取决于原 BIU 已经构成瓶颈、目标 BIU 有余量，而且缓存重热与迁移开销较低。说明书给出 107 和 195 GB/s 的情形，但没有交代完整测量条件或 195 GB/s 的聚合口径，不能据此预测迁移后的实际带宽。

共享资源过载标记与线程标记的保存位置不同

原图 4A、4B 把 BIU 标记画在线程 2.C 的记录上，同组其他线程分别保存自己的标记。图 5 把 CPU cluster 的历史观测与线程标记放到同一条事件轴上。源 CPU cluster 的过载标记指向共享 BIU 而留在源端。线程 2.C 在上下文切换或时间片耗尽时被调度到目标 CPU cluster 后，线程标记仍随它保留。

在说明书给出的实施方式中，性能控制器可以另发清除通知。源端最近有无过载、目标端有无过载、迁移线程原先是否使用过拥塞资源，分别对应不同的状态。迁移决策可读取先前置位的线程标记，不必把源端 BIU 的拥塞状态传播给目标。
