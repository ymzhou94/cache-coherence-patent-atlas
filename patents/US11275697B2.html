合并 TLB 失效请求时保留电源状态边界

Translation lookaside buffer invalidation for merged invalidation requests across power boundaries

目标 CPU 或 GPU 在合并请求期间进入低功耗状态时，哪些 TLB 失效仍须发送？

工程要点

TLB 维护逻辑合并清除请求，在检测到目标处理器转入指定非活动状态后可丢弃被覆盖的合并请求。

成立条件
只在已确认的状态转换覆盖相关维护时才可省去该批消息，目标核恢复后的新请求需根据其时间区间判断。
验证方法
以相同请求地址分别将一组失效请求放在目标状态转换之前和之后。对齐状态转换、合并判定及实际发出到目标的失效消息。

工作机制

CPU 与 GPU 可以处于不同电源域。内核更新页表时，需要按地址转换缓存状态清除可能过时的 TLB 条目。多个失效请求合并后，目标处理器可能已完成一次清除这些条目的电源状态转换。

合并前给每条 TLB 失效请求关联接收时间，并与目标处理器的活动时间线比较。在原文的转换会清除 TLB 的实施例中，可丢弃被该转换覆盖的请求。同一批中属于后续活动区间的请求仍需发出。

  1. 记录两条失效请求

    分别关联接收时间。合并结构保留能够比较时间先后的信息。

  2. 读取电源状态指示

    按目标处理器的活动和非活动指示建立时间线。

  3. 判断是否已清除受影响状态

    原文相关实施方式在进入非活动状态时清除 TLB，可以覆盖较早请求。

  4. 保留后续活动区间的请求

    如果同批还有目标重新活动后的请求，则依据它继续发送 TLBI。

  • 调度事件与硬件状态事件分别观察

实验与取舍

何时有效
可减少发送给已清除地址转换状态的组件的冗余维护事务。
代价和限制
如果目标域保留 TLB 条目，丢弃请求可能保留旧映射。状态通知和请求时间线都要可比较。
验证指标
按目标电源域记录失效请求、合并次数、实际发送次数及映射更新至失效完成的延迟。

教学算例

初始条件
T0 和 T1 收到两个失效。目标处理器随后进入会清空 TLB 的非活动状态，恢复后又收到第三个失效。
处理结果
合并时可以略过已由清除覆盖的前两个请求，第三个仍发往目标。
结果解读
目标转换是否使 TLB 内容无效取决于电源域和实现。单凭线程睡眠或空闲状态标签无法确认为同一转换。

权利要求与出处

独立权利要求为第 1、8、15 项。下方列出部分权利要求的中文释义。

权 1
接收并合并两个 TLB 清除请求，检测目标处理器已进入非活动状态，并据此丢弃合并请求。
权 8
程序介质权项限定相同的接收、合并与状态判定步骤。
权 15
装置权项把失效判断落到与内存耦合的处理器。
