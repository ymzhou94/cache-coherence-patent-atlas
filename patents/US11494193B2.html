协处理器完成工作时，CLPC 用哪一个控制量恢复 CPU

Serialization floors and deadline driven control for performance optimization of asymmetric multiprocessor systems

CPU 等待 GPU 或神经引擎期间，CLPC 可能已降到低控制量。工作返回 CPU 时怎样决定恢复到什么状态？

核心结论

卸载前按线程组保存 CPU 的 control effort。结果交付后，用保存值计算新的控制初值。对工作高度串行的情况，可以恢复更高的初值，以缩短 CPU 恢复执行后的爬坡。

保存点在卸载提交，重置点在结果交付

原图 3 明确给出 AP 的 CPU complex、OS 服务和 GPU 或神经引擎接力。说明书 0056 和 0063 将工作提交方定义为运行 OS 程序的应用处理器，独权则约束跨处理器与协处理器的控制量保存和重置。

图 1 将 OS 提交、协处理完成通知和 CLPC 对同一线程组的控制串起来。保存值用于处理器侧控制。协处理器仍有自己的控制量。

CPU 的 OS 线程是否就绪、何时重新被调度，以及 CPU 何时达到选定的 DVFS 状态，属于不同事件。独权规定的是 control effort 的保存与重置时点。

CPU 忙闲计数决定恢复幅度

图 2 示出等待结果与准备后一帧两种路径。前者在协处理窗口内几乎没有 CPU busy，后者可用这段时间继续计算。图 3 按这两个计数边界生成串行程度因子。

在原文给出的乘积示例中，控制下限等于保存 CE 乘以串行程度、耗时函数和策略因子。完全串行且另外两项取 1 时，可以恢复保存值。流水化使串行因子趋近于 0。权利要求 3–5 分别约束不同缩放因子。

完成时限反馈是说明书的另一条控制路径

图 4 把 deadline 超前或落后的误差分给 CPU 和 GPU。归档 0178 指出单独执行只能估计关键性的一部分。两个引擎并行执行仍可能存在关键路径。

复核时比较相同 GPU 工作时长、不同 CPU 重叠度的窗口，记录保存与恢复的 CE、实际 OPP、结果交付至下一段完成的时间以及额外能量。
