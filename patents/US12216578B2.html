用两级 token 恢复分散设备请求的发出顺序

Request ordering in a cache

设备请求按地址分到不同流水线，又按空位进入不同缓冲。控制器怎样从这些物理位置找回严格的到达顺序，同时允许其他设备的请求独立推进？

核心结论

严格流用该处理器的二级 token FIFO 记录请求所在流水线，再用一级 FIFO 记录流水线内的缓冲。发送时按两级队首定位最老请求。有限重排流可只用独立的一级 token 维持同一设备顺序。

设备地址确定存放位置，token 另存到达顺序

从图 1 左侧跟住一笔请求。处理器的 bank 选择接口先按设备地址选处理流水线，再看该流水线的哪个缓冲有空间。地址映射与空位分配都不提供时间顺序，不能仅从缓冲编号推断谁先到。

对严格流，接口把流水线编号放到该处理器的二级 token FIFO，并把缓冲编号放到该流水线对应的一级 FIFO。原始地址、请求类型和数据仍只保存在实际缓冲，token 用来还原位置。另一个处理器可用独立的两级顺序记录。

发出时两级队首先后决定可读位置

在图 2 的实例中，二级队首依次指向 A、B、A。第一笔必须从 A 找。再读 A 的一级队首，得到缓冲 1。若缓冲按 FIFO 存放相应请求，直接取最老项。说明书另允许一级条目带请求 ID，以在非 FIFO 的请求缓冲里定位。

第二笔 B 即使已在另一条流水线准备好，也不属于本次严格队首。这里使用的是请求从缓存向设备发出的顺序。设备处理时间和返回应答要另按接口协议定义。

有限重排只保存该设备需要的次序

图 3 的有限重排条目仍按空闲位置分散在多个缓冲，但同一设备地址在这一例中映射到同一条流水线。独立一级 FIFO 足以定位同设备最老请求。其他流水线可各自提名，无需从同一个二级 FIFO 决定次序。

严格流和有限重排流可能同一周期在某条流水线产生候选。局部出口可采用 FIFO、优先级或轮询。各流水线提名后，还要由相应出口选择哪笔能够占用设备接口。

设备暂不能接收时，等待会怎样传播

图 4 固定 A1、B1、A2 到达顺序和设备接收状态。严格流先等 A1，这会推迟可以在 B 侧接收的 B1。有限重排流保留 A1 先于 A2，可用空闲的第 0 周期先发 B1。表 6 对照发出端点。

图中设定接口每周期接受一笔，并让 A 在窗口内暂时失去接收能力。通过在外发接口记录候选、选择与实际接受，可以区分等待来自两级顺序，还是来自设备接收门槛。

同周期可发多笔时，先找最老的共同前缀

图 5 展开说明书披露的多发射实施例。若二级队首连续三项都指向同一流水线，控制器可以一起考虑这三笔最老请求。再看该流水线的一级 FIFO，若前两项来自同一个允许多读的缓冲，这两项可在同周期发出。后一项和下一条流水线的请求继续等候。

同时发出只是可选带宽。硬件还需要读出多个请求、提供设备接口资源，并维持要求的顺序。原文也披露一次只发一笔的实施例。

授权权利要求关注的是定位与发出顺序

权利要求 1、8、15 关注两级 token 对严格有序请求的定位与发出。权利要求 3、4、10、11、17、18 增加不使用二级队首的有限重排路径，权利要求 6、13、20 涉及其他处理器独立记录。图 5 的同周期多发机制来自说明书。
